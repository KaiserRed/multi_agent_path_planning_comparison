\section{ПРОЕКТИРОВАНИЕ ПРОГРАММНОГО КОМПЛЕКСА}

\subsection{Выбор стека технологий}

При проектировании программного комплекса были выбраны следующие технологии:

\begin{itemize}
    \item Python 3.12 --- основной язык разработки, обеспечивающий высокую скорость прототипирования и обширную экосистему библиотек для научных вычислений;
    \item Pygame 2.6 --- библиотека для создания графического интерфейса и визуализации, предоставляющая низкоуровневый доступ к 2D-рендерингу при минимальных зависимостях;
    \item NumPy --- библиотека для работы с многомерными массивами, используемая для представления сеточной карты мира;
    \item Pandas --- библиотека для обработки табличных данных, применяемая в подсистеме пакетного тестирования для агрегирования результатов экспериментов;
    \item Matplotlib --- библиотека для построения графиков, используемая для автоматической генерации визуализаций результатов пакетных экспериментов;
    \item JSON --- формат сериализации сценариев (карт), обеспечивающий совместимость и читаемость;
    \item PyInstaller --- инструмент для сборки Python-приложения в автономный исполняемый файл, обеспечивающий кроссплатформенное распространение без необходимости установки интерпретатора Python.
\end{itemize}

Выбор Python обусловлен тем, что целью работы является сравнение алгоритмов, а не достижение максимальной производительности отдельных реализаций. Python позволяет реализовать все алгоритмы в единой среде с одинаковыми накладными расходами интерпретатора, что обеспечивает корректность сравнения. Библиотека Pygame была выбрана вместо веб-фреймворков или Qt, поскольку она обеспечивает прямой контроль над кадровым циклом, что критично для покадровой визуализации работы алгоритмов. Использование PyInstaller позволяет собирать приложение в единый исполняемый файл для операционных систем Windows, Linux и macOS, что обеспечивает кроссплатформенность и упрощает распространение.

\subsection{Базовые классы алгоритмов}

Ключевым архитектурным решением является использование паттерна <<Стратегия>> (Strategy) для подключения алгоритмов. Все MAPF- и MRTA-алгоритмы реализуют единый интерфейс, определённый базовыми классами \texttt{MAPFPlanner} и \texttt{MRTAPlanner}.

\subsubsection{Класс MAPFPlanner}

Базовый класс \texttt{MAPFPlanner} определяет контракт для всех алгоритмов поиска бесконфликтных маршрутов:

\begin{itemize}
    \item метод \texttt{plan(world, agents)} принимает модель мира и список агентов, возвращает словарь вида \texttt{\{agent\_id: [(pos, time), ...]\}} или \texttt{None} при неудаче;
    \item атрибуты класса содержат метаданные алгоритма: отображаемое имя (\texttt{DISPLAY\_NAME}), тип архитектуры (\texttt{IS\_CENTRALIZED}), режим работы (\texttt{IS\_ONLINE}).
\end{itemize}

Метаданные используются интерфейсом для отображения информации об алгоритме и симулятором для выбора стратегии выполнения. Единый формат возвращаемого значения --- список позиций с временными метками --- обеспечивает взаимозаменяемость алгоритмов: любой MAPF-планировщик может быть использован в качестве навигационного модуля для MRTA без модификации кода симулятора.

\subsubsection{Класс MRTAPlanner}

Базовый класс \texttt{MRTAPlanner} определяет контракт для алгоритмов распределения задач:

\begin{itemize}
    \item метод \texttt{plan(world, agents, tasks)} принимает мир, агентов и задачи, возвращает словарь \texttt{\{agent\_id: [Task, ...]\}};
    \item атрибут \texttt{ASSIGNMENT\_MODE} определяет режим назначения: \texttt{"online"} или \texttt{"queue"}.
\end{itemize}

Режим назначения является ключевым проектным решением, определяющим поведение симулятора:

\begin{itemize}
    \item в режиме \texttt{online} каждому агенту назначается по одной задаче; после её завершения планировщик вызывается повторно для освободившегося агента с оставшимися задачами;
    \item в режиме \texttt{queue} планировщик строит полную цепочку задач для каждого агента за один вызов; симулятор последовательно выполняет элементы цепочки без перепланирования.
\end{itemize}

Такое разделение позволяет реактивным алгоритмам (венгерский, жадный) адаптироваться к изменениям в реальном времени, а планирующим алгоритмам (аукционы, потоковые) оптимизировать глобальную стоимость назначения.

\subsection{Модель данных}

\subsubsection{Класс World}

Класс \texttt{World} представляет среду в виде двумерной сеточной карты. Внутреннее представление --- массив NumPy размером $H \times W$, где значение 1 обозначает препятствие. Метод \texttt{is\_free(x, y, time, reserved)} проверяет доступность клетки с учётом как статических препятствий, так и динамических резерваций (множество троек $(x, y, t)$, зарезервированных другими агентами).

\subsubsection{Класс Agent}

Класс \texttt{Agent} хранит текущую позицию агента $(x, y)$, целевую позицию $(goal\_x, goal\_y)$, построенный путь и индекс текущего шага. Метод \texttt{set\_path} назначает агенту новый путь, \texttt{next\_step} возвращает следующую позицию и продвигает индекс. Каждому агенту автоматически назначается уникальный цвет для визуализации.

\subsubsection{Класс Task}

Класс \texttt{Task} описывает задачу для MRTA-планировщика: уникальный идентификатор, целевая позиция $(x, y)$, приоритет, ссылка на назначенного агента и флаг завершения. Задачи создаются из целевых позиций сценария при выборе MRTA-режима.

\subsubsection{Класс SceneData}

Класс \texttt{SceneData} --- алгоритмо-независимое описание сценария: размеры сетки, позиции препятствий, стартовые позиции агентов и целевые позиции. Один и тот же сценарий может использоваться как для MAPF (цели --- конечные точки агентов), так и для MRTA (цели --- задачи для распределения). Сериализация выполняется в формате JSON, что обеспечивает переносимость и возможность повторного использования сценариев.

\subsection{Форматы входных файлов сценариев}

Программный комплекс поддерживает три формата описания сценариев, что обеспечивает совместимость как с внутренним представлением, так и с общепринятыми наборами тестовых данных из репозитория Moving\,AI Lab~\cite{sturtevant2012benchmarks}. Загрузка выполняется единой функцией \texttt{load\_map\_file}, которая определяет формат по расширению файла и вызывает соответствующий парсер.

\subsubsection{Внутренний формат JSON}

Сценарии, созданные в редакторе карт программного комплекса, сохраняются в формате JSON. Файл содержит поля \texttt{grid\_width}, \texttt{grid\_height}, \texttt{obstacles}, \texttt{agent\_starts} и \texttt{goals}, каждое из которых соответствует одноимённому атрибуту класса \texttt{SceneData}. Координаты препятствий, стартовых позиций и целей представлены массивами пар $(x, y)$. Формат легко читается и поддаётся ручному редактированию.

\subsubsection{Формат Moving\,AI .map}

Формат \texttt{.map} описывает только статическую структуру среды --- размеры сетки и расположение препятствий. Файл начинается с заголовка, содержащего тип карты (\texttt{type}), высоту (\texttt{height}) и ширину (\texttt{width}), за которым следует ключевое слово \texttt{map} и далее --- сетка символов размером $H \times W$. Каждый символ кодирует тип клетки: символы <<\,.\,>>, <<G>> и <<S>> обозначают проходимые клетки, любые другие символы (в частности <<@>>, <<O>>, <<T>>, <<W>>) интерпретируются как препятствия. Стартовые позиции агентов и цели в формате \texttt{.map} не задаются, поэтому при импорте такого файла они должны быть сгенерированы программно либо загружены из связанного файла \texttt{.scen}.

\subsubsection{Формат Moving\,AI .scen}

Формат \texttt{.scen} описывает набор тестовых пар <<старт--цель>> для конкретной карты. Файл начинается со строки \texttt{version 1}, далее каждая строка содержит девять полей, разделённых табуляцией: номер класса сложности (\texttt{bucket}), имя файла карты, ширина и высота карты, координаты старта $(s_x, s_y)$, координаты цели $(g_x, g_y)$ и оптимальная длина пути для одиночного агента. Пример строки:

%\begin{verbatim}
%7  random-32-32-20.map  32  32  5  16  31  24  31.313708
%\end{verbatim}

В разработанном программном комплексе файл \texttt{.scen} интерпретируется как \emph{библиотека задач}: каждая строка задаёт один возможный сценарий движения для отдельного агента, а из множества таких задач при пакетном тестировании формируется требуемое число одновременно действующих агентов. Соответствующий файл \texttt{.map} (определяемый по полю имени карты в строках \texttt{.scen}) загружается автоматически и используется как источник информации о препятствиях; если файл карты находится в той же директории, что и файл сценариев, операция выполняется прозрачно для пользователя.

\subsection{Система регистрации алгоритмов}

Для обеспечения расширяемости системы реализован центральный реестр алгоритмов (модуль \texttt{registry}). Реестр представляет собой словарь, содержащий экземпляры всех доступных планировщиков, сгруппированные по типу (\texttt{"MAPF"} и \texttt{"MRTA"}).

Функция \texttt{get\_planner(algo\_type, display\_name)} выполняет поиск планировщика по типу и отображаемому имени. Такая архитектура позволяет добавлять новые алгоритмы без модификации существующего кода: достаточно реализовать подкласс \texttt{MAPFPlanner} или \texttt{MRTAPlanner}, импортировать его в \texttt{registry.py} и добавить экземпляр в соответствующий список.

Реестр используется как интерактивным интерфейсом (для формирования списка алгоритмов на экране выбора), так и подсистемой пакетного тестирования (для перебора комбинаций алгоритмов).

\subsection{Симулятор: планирование и выполнение}

Класс \texttt{Simulator} является центральным координирующим компонентом, объединяющим планирование и пошаговое выполнение для обоих режимов работы.

\subsubsection{Этап планирования}

Метод \texttt{plan()} выполняет полный цикл планирования с замером времени и памяти (\texttt{tracemalloc}):

\begin{enumerate}[arabic]
    \item В режиме MAPF: вызывается \texttt{planner.plan(world, agents)}, полученные пути назначаются агентам.
    \item В режиме MRTA: процесс двухэтапный:
    \begin{itemize}
        \item MRTA-планировщик распределяет задачи: \texttt{planner.plan(world, agents, tasks)};
        \item навигационный MAPF-планировщик строит маршруты к первым задачам: \texttt{\_nav\_all(agents)}.
    \end{itemize}
\end{enumerate}

Метод \texttt{\_nav\_all} является ключевым связующим элементом между MRTA и MAPF. Если задан навигационный планировщик (\texttt{nav\_planner}), он вызывается для совместного построения бесконфликтных путей всех агентов. В противном случае используется последовательный fallback в стиле CA*: агенты планируются один за другим, каждый --- с учётом путей предыдущих через общую таблицу резерваций.

\subsubsection{Этап выполнения}

Метод \texttt{step()} выполняет один временной шаг симуляции:

\begin{enumerate}[arabic]
    \item каждый агент, имеющий невыполненный путь, перемещается на следующую позицию;
    \item обновляется метрика SOC (каждое перемещение увеличивает счётчик на 1);
    \item в режиме MRTA проверяется завершение задач: если агент достиг позиции назначенной задачи, задача помечается как завершённая;
    \item при завершении задачи в queue-режиме из очереди извлекается следующая задача, и маршрут достраивается методом \texttt{\_path\_to\_single};
    \item при завершении задачи в online-режиме вызывается повторное планирование для освободившегося агента.
\end{enumerate}

\subsubsection{Сбор метрик}

\subsection{Подсистема пакетного тестирования}

Подсистема пакетного тестирования обеспечивает автоматизированное проведение серий экспериментов с различными комбинациями алгоритмов и параметров среды.

\subsubsection{Конфигурация эксперимента}

Класс \texttt{BatchConfig} определяет все параметры пакетного эксперимента:

\begin{itemize}
    \item списки выбранных MAPF- и MRTA-алгоритмов;
    \item диапазон числа роботов: минимум, максимум, шаг;
    \item параметры процедурной генерации карты: размеры сетки, плотность препятствий, стратегия размещения, флаг проверки достижимости;
    \item число сценариев на каждое значение числа роботов (для статистической достоверности);
    \item список импортированных файлов карт в форматах JSON и \texttt{.map} (\texttt{imported\_maps});
    \item список файлов \texttt{.scen} для использования в качестве источника пар <<старт--цель>> (\texttt{scen\_files});
    \item таймаут на этап планирования и таймаут на этап симуляции;
    \item путь к директории вывода.
\end{itemize}

Поля \texttt{imported\_maps} и \texttt{scen\_files} являются взаимоисключающими: при заполнении одного из них другое сбрасывается интерфейсом, а параметры процедурной генерации игнорируются.

\subsubsection{Генерация сценариев}

Класс \texttt{SceneGenerator} создаёт сценарии для экспериментов. Источник сценария выбирается по приоритету: при наличии файлов \texttt{.scen} они используются в первую очередь; при наличии импортированных карт сценарий формируется на их основе; в противном случае выполняется процедурная генерация.

Процедурная генерация поддерживает четыре стратегии размещения агентов и задач:

\begin{itemize}
    \item uniform --- агенты и задачи размещаются на случайных свободных клетках равномерно;
    \item clustered --- агенты концентрируются в центре карты, задачи --- у периметра;
    \item counter --- агенты слева, задачи справа (встречные потоки);
    \item min\_dist --- гарантируется минимальное расстояние между стартовыми позициями.
\end{itemize}

Генератор выполняет проверку достижимости каждой пары <<старт--цель>> с помощью поиска в ширину (BFS) и повторяет генерацию при обнаружении недостижимых целей (до 20 попыток).

\subsubsection{Использование файлов .scen в пакетном режиме}

Для интеграции файлов формата \texttt{.scen} в пакетный режим реализован класс \texttt{ScenLibrary}, представляющий собой кэшированное в памяти описание загруженного файла. При создании библиотеки файл \texttt{.scen} разбирается единожды, после чего сохраняются размер сетки, список препятствий и полный набор пар <<старт--цель>>. Внутри \texttt{SceneGenerator} поддерживается словарь \texttt{\_scen\_cache}, ставящий в соответствие пути к файлам уже загруженные библиотеки, что исключает повторное чтение при многократном обращении в течение одного эксперимента.

Метод \texttt{sample(n\_robots, seed)} формирует сценарий для требуемого числа агентов из библиотеки следующим образом:

\begin{enumerate}[arabic]
    \item на основе значения \texttt{seed} создаётся независимый генератор псевдослучайных чисел;
    \item копия списка пар <<старт--цель>> перемешивается этим генератором;
    \item перемешанный список последовательно сканируется; пара включается в сценарий, если её стартовая позиция ещё не использована;
    \item процесс завершается, когда набрано \texttt{n\_robots} пар с попарно различными стартовыми позициями.
\end{enumerate}

Дедупликация выполняется только по стартовым позициям, поскольку совпадение целевых позиций двух агентов допустимо. Если в библиотеке недостаточно различных стартовых позиций для требуемого числа агентов, сценарий помечается как несформированный.

\subsubsection{Запуск и вывод результатов}

Класс \texttt{BatchRunner} перебирает все комбинации (MRTA-алгоритм $\times$ MAPF-алгоритм $\times$ число роботов $\times$ seed сценария) и для каждой создаёт экземпляр симулятора. Таймауты реализованы через \texttt{threading.Timer}: при превышении установленного времени на этап планирования или этап симуляции прогон помечается как неуспешный.

Результаты агрегируются в табличный объект \texttt{pandas.DataFrame} и экспортируются модулем \texttt{plotter}:

\begin{itemize}
    \item CSV-файл со всеми метриками каждого прогона. Состав колонок приведён в таблице~\ref{tab:batch_csv};
    \item четыре графика (Matplotlib): Makespan, SOC, время планирования и доля успешных прогонов (Success Rate) в зависимости от числа роботов.
\end{itemize}
